# Historical inventory catalogue and project bridge

## What this slice does

Open `frontend/inventory-catalogue.html` with its sibling styles and scripts present. The page starts empty. It keeps separately labelled selected-folder snapshots, shows a scoped overview, searches their recorded paths while storage is unplugged, and exports a chosen project into the existing manual planning workspace.

This is a useful first offline catalogue, not a live drive connection. No default navigation, existing application, scanner route, command-line user-folder selector, provider, mutation, restore operation or deployment is introduced. The synthetic-only observation adapter stays unchanged.

### First journey

1. Open one snapshot JSON. Review its original folder label, claimed date and complete/partial status, then give the separate catalogue record a useful location label.
2. Add further snapshots. A record might be labelled “Blue external drive · photos”, but this remains your label for one selected-folder observation, not verified physical-drive identity.
3. Compare each card's top-level content groups and listed observed file sizes. Search across all records, including historical records of disconnected storage. Each result names its recorded location and source date so you know which storage to reconnect and check in your own tools.
4. Select plain observed files or folders across records. The interface prevents overlapping folder/descendant choices within a record. It cannot establish whether different records describe the same physical storage.
5. Create and download a manual project plan. Open it in `manual-workspace.html` to choose intended homes, planned backup targets and restore checklists. The export does not replace any existing workspace or execute anything.
6. Save the catalogue privately and acknowledge the download only after confirming it in Downloads. Reopen that file explicitly to resume. Temporary project selections are not part of the catalogue; export a manual plan to retain them.

The illustrative snapshots in `prototypes/inventory_catalogue/` were generated by observing newly created, owned temporary directories with fixed test names and placeholder file bytes. They are examples, never user-drive evidence. The production bridge is still exercised only on owned fixtures.

## Reading the overview correctly

- Each card is one saved selected-folder snapshot, not necessarily one unique drive. A person can keep separate folders or dates for the same drive; identical labels, source references or paths never cause automatic merging.
- The card shows its original observation timestamp as a claim, including its timezone. Renaming the card never changes the embedded original folder label, timestamp or entries.
- Logical-size composition sums only listed `observed` file paths. Directory sizes and uncertain-status file bytes are excluded. Hard links and repeated source snapshots can represent the same bytes more than once. These figures are not used/free space, recoverable capacity, deduplicated physical allocation or backup billing.
- Complete means complete within that selected folder's bounded producer policy at the claimed time, not a whole-drive survey or an atomic snapshot. Partial records retain their gaps and may omit entire branches.
- Current connection, physical identity, authenticated versions, dependencies, available capacity and protection are unknown. Missing search results never establish that a file is absent. The catalogue cannot notice a reconnection or refresh itself.
- Four named content groups are shown on a card; any remaining groups are explicitly aggregated. All recorded entry matches remain accessible through 50-row pagination with total and page counts. Nothing is silently cut out of search.
- Show details exposes original source labels, dates, source references, record keys, coverage, stop reasons, errors and exclusion counts. It changes presentation only.

## Producer and trust boundary

`backend/inventory_snapshot.py` exposes `observe_snapshot(selection, source_label, *, cancel=None, progress=None)`. It accepts the existing live process-local `ReadOnlySelection`, consumes it through `observe_once`, and projects display metadata. It does not accept an inventory dictionary, open a path itself, add an OS permission grant or register a public route/CLI.

The existing scoped observation policy remains metadata-only, no filesystem crossing, at most 2,000 entries, 500 entries per directory, depth 8 and five cooperative seconds. No content hashing is enabled. A blocking OS call can exceed the cooperative deadline, and metadata access can update access times. Unsupported platforms abstain. Cancellation, revocation, failed/root-changed observations and callback failures supply no snapshot. Names or metadata outside the smaller display contract cause an explicit whole-projection rejection after the selection is retired; no partial export is manufactured.

The snapshot excludes absolute selected-root paths, device/inode identity, fingerprints, hashes, allocation estimates and execution/recovery authority. It contains a user-supplied folder label, claimed source date/reference, coverage, relative entry paths/kinds/statuses, decimal-string logical sizes and gap summaries.

Saving a snapshot as JSON destroys any process-local provenance. Every imported file is therefore an unauthenticated historical claim, regardless of whether it conforms to the format or came from the supplied exporter. A scan reference is an opaque reference, never authentication. The schema has no trusted flag. Structurally valid user JSON never becomes a live observation, authenticated version, physical drive or backup verification.

## Formats and bounds

- Snapshot: `disk-organiser/inventory-snapshot/v1`; at most 1 MiB canonical UTF-8, 2,000 entry records including the selected-folder record and 32 exclusion reasons.
- Catalogue: `disk-organiser/inventory-catalogue/v1`; at most 32 labelled snapshot records, 10,000 aggregate entries and 4 MiB canonical UTF-8. The aggregate entry/byte bounds can be reached before the record limit.
- Input file size is checked before allocation, its read length is checked afterwards, UTF-8 decoding is fatal, and a BOM is preserved for strict rejection. The parser rejects duplicate/escaped-duplicate keys, extra fields, future versions, malformed Unicode, unsupported controls, repeated paths, missing/wrong-kind parents and contradictory complete/gap states.
- Decimal strings preserve large byte values without JavaScript integer rounding. The format deliberately contains no JSON numbers or Booleans. Counts and sizes have explicit bounds.
- Parsing is limited to 12 nested containers and 150,000 values. Canonical byte accounting runs before whole-artifact serialisation. Failed admission, rename or export leaves prior catalogue records unchanged.
- Labels use at most 240 Unicode code points; source-relative paths at most 1,024. Manual exported item labels are shortened to 240 code points when necessary, while the complete original relative path remains in both the location and provenance notes.

The browser model is independent of the manual plan schema and validates its generated plan with the existing model. Per-item notes preserve the original folder label, original relative path, source date/reference, complete/partial scope and explicit untrusted-claim caveat. The newly named drive record and project membership are user decisions. Intended homes are absent; target lists are empty; protection is unknown. Later manual changes do not rewrite the source notes, although they remain editable user-authored notes and are not tamper-proof provenance.

## Local state and interruption

No browser storage, telemetry, remote font/script, request, provider or account is used. A restrictive CSP denies connections and form submissions. Labels and paths are rendered as text. The sole file read is the JSON artifact explicitly selected by the user. Source names and path strings are never resolved.

Import is preview-before-add/replace. Adding a snapshot creates a distinct record. Opening a catalogue explicitly replaces the current one and clears temporary selections. Cancellation, newer file pickers, edits during asynchronous reads and navigation retire stale pending work. Confirmations are one-use; repeated submit events do not duplicate records or exports. Failed saves retain the catalogue; successful activation reports only a requested download. Unsaved-state acknowledgement is tied to the current catalogue revision. Source record keys keep selection and keyboard focus separate even when visible labels match.

Catalogues and plans are private plaintext artifacts, not encrypted files. They may contain private relative names, dates, sizes and notes. No exclusive backup offer or partner programme is claimed. Provider comparison and commercial terms require separately verified data and remain outside this slice.

```sh
python -m pytest -q backend/tests/test_inventory_snapshot.py backend/tests/test_observation_session.py
npx jest --config jest.config.js --runInBand frontend/__tests__/inventory-snapshot-model.test.js

npx playwright test --config playwright.inventory-catalogue.config.js
```

The backend tests use only fresh owned temporary fixtures and include metadata-only observation, cancellation/revocation/failure, unsupported platforms, hostile names, dictionary-forgery rejection, import isolation and a fresh producer → browser parser → manual-plan roundtrip.
